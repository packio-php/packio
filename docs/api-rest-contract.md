# REST API Contract

Date: 2026-06-27

Packio exposes a stateless JSON REST API under `/api/v1`.

## Decisions

- Versioned application endpoints use `/api/v1`.
- OpenAPI JSON is available at `/api/doc.json` and `/api/v1/doc.json`.
- Swagger UI is available at `/api/doc`.
- REST authentication uses user-scoped API access tokens, not Composer registry tokens.
- API clients may send either `Authorization: Bearer <token>` or Repman-compatible `X-API-TOKEN: <token>`.
- API access tokens are stored hashed, may be revoked or expired, and expose the plain value only once on creation or regeneration.
- API errors use the machine-readable shape `{"error":{"code":"...","message":"...","details":{...}}}`.
- Protected routes combine API-token authentication, token scopes, existing organization context, and existing RBAC permissions.
- Admin REST endpoints require both `admin` token scope and the existing `admin.access` permission.
- API docs and `/api/v1/health` stay public by default for self-hosted automation and deployment checks.

## Documentation

- Browser UI: `http://localhost:8080/api/doc`
- Current OpenAPI JSON: `http://localhost:8080/api/doc.json`
- Versioned OpenAPI JSON: `http://localhost:8080/api/v1/doc.json`
- Generated artifact: `public/openapi.json`

The OpenAPI artifact is generated by `composer openapi-generate`. CI validates that the committed artifact is up to date with `composer openapi-check`.

## Authentication

Create a REST API token from the UI or API, then send it with either header:

```bash
curl -H "Authorization: Bearer $PACKIO_API_TOKEN" \
  http://localhost:8080/api/v1/me
```

```bash
curl -H "X-API-TOKEN: $PACKIO_API_TOKEN" \
  http://localhost:8080/api/v1/me
```

Composer registry tokens are separate credentials. Registry tokens can access the Composer registry protocol, but they are not accepted as REST API tokens.

### Banned accounts

An existing API token is checked against its owner's current account state on
every request. A banned owner receives `403 Forbidden`; the response preserves
the standard error envelope and has the stable code `account_banned`:

```json
{
  "error": {
    "code": "account_banned",
    "message": "Account has been banned.",
    "details": {
      "reason": "Violation of project rules.",
      "banned_at": "2026-08-22T10:00:00+00:00"
    }
  }
}
```

The response never exposes the banning administrator's identity. A blocked
request does not update the token's `last_used_at`. After a manual unban, the
same non-revoked token works again on its next request. Composer registry tokens
are subject to the same owner-state check for private access; they are not REST
API credentials.

## Scope Model

The API supports coarse scopes and resource scopes.

- `read`: broad read access to non-admin API resources allowed by RBAC.
- `write`: broad write access to non-admin API resources allowed by RBAC.
- `admin`: required for `/api/v1/admin/*` in addition to the user's admin role.
- Resource scopes include `tokens:read`, `tokens:write`, `sources:read`, `sources:write`, `packages:read`, `packages:write`, `releases:read`, `releases:write`, `webhooks:read`, `webhooks:write`, `members:read`, `members:write`, `organizations:read`, and `organizations:write`.
- Wildcards: `<family>:*` covers both actions of one family, `*` grants every scope, and `admin:*` covers every `admin:` scope. The admin role is still required for admin endpoints.

Source responses include `provider_config.webhook_secret` only when the caller may manage the source (or is a site admin) and the token grants `sources:write`. Otherwise the key is removed. Webhook secrets are encrypted at rest.

Admin scope is only granted to users with the admin role. A regular user cannot create an admin REST API token through the API, and a raw admin-scoped token still cannot access admin endpoints without the admin role.

## Authorization

Organization-scoped endpoints resolve the organization from the `organization` route parameter, then use the existing organization membership and RBAC policies.

- Organization management actions such as update, delete, member role changes, invitations, and registry-token management require owner-level permissions.
- Read actions still require valid organization membership and the matching token scope.
- Cross-organization resource identifiers must not grant access to resources from another organization.
- Admin endpoints are guarded separately by the admin role, `admin` token scope, and `admin.access`.

## Endpoint Groups

- System: health, current user, OpenAPI JSON, Swagger UI.
- User API tokens: list, create, revoke, regenerate.
- Organizations: list, create, show, update, delete.
- Organization members and invitations: list, create/update/revoke/delete where applicable.
- Registry tokens: list, create, revoke, regenerate.
- Registry overview: organization package overview.
- Source providers, provider instances, provider authorizations, and sources.
- Source webhooks: register, rotate secret, delivery events, reprocess.
- Packages and releases, including package/release destructive actions and release activity updates.
- Admin: users, organizations, packages, sources, jobs, and runtime settings.

## Error Format

Validation and application errors use the same envelope:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Invalid request data.",
    "details": {
      "name": ["Name is required."]
    }
  }
}
```

Authentication and authorization failures use `401` or `403` with the same `error` envelope. Rate-limited requests return `429`.

`account_banned` is a `403` authorization response that takes precedence over
email-verification checks for an otherwise valid API token.

### Request-mapping failures

DTO request mapping failures have three explicit response branches:

1. Every `/api/*` route returns `422 Unprocessable Entity` using the validation
   envelope above: `error.code` is `validation_failed`, `error.message` is
   `Invalid request data.`, and `error.details` contains normalized field-error
   lists. This path boundary is authoritative regardless of the `Accept` header.
2. A browser or Inertia route with an applicable `#[ValidationFailed]` policy
   uses that policy's established JSON or redirect response, notification, and
   old-input rules. Only fields explicitly allowlisted by that policy may be
   retained as old input; request bodies are never retained wholesale.
3. A route without an applicable `#[ValidationFailed]` policy keeps the mapping
   package's fallback response unchanged. In particular, unannotated browser
   routes do not gain redirects, notifications, or old-input persistence by
   inference.

Valinor's own error messages embed the submitted values, so mapping-failure
details never surface them verbatim. Every normalized field error uses the
stable message `Invalid value.`; the client signal is carried entirely by the
snake_case field key (or `root` for a top-level failure). This applies to all
three branches.

The fallback branch is produced after the Inertia middleware and therefore
would normally receive Inertia response decoration (`Vary: X-Inertia`,
`X-Inertia` headers). An internal `X-Packio-Inertia-Fallback` marker is attached
to the fallback response and removed by
`StripPackageMappingErrorInertiaDecorationMiddleware`, which also strips the
Inertia decoration so the fallback `application/json` response stays clean.

Mapping source values and normalized error details are not written to logs.

### Post-mapping semantic validation

Structural mapping and semantic validation are two independent, explicitly
switched stages:

1. `#[MapRequest]` maps raw input into a DTO. Mapping/input failures follow the
   three branches above and never run the Yiisoft validator.
2. `#[ValidateMappedRequest(Dto::class)]` explicitly opts a route into semantic
   validation of the mapped DTO with the Yiisoft validator. A route without this
   attribute is mapper-only by design. Every DTO declared with
   `ValidateMappedRequest` on the route is validated exactly once, in
   declaration order; the first invalid DTO short-circuits
   the pipeline before the handler and before any domain mutation.
3. `#[ValidationFailed(...)]` never enables validation and never registers
   middleware. It only overrides the failure response (redirect, message,
   notification, JSON status, old-input allowlist). A route carries at most
   one such policy (more than one is an invalid configuration); it applies to
   every validated DTO on the route. For mapping errors it applies only to the
   route's first mapped DTO. A route can carry validation without it, and it
   without validation
   would be an invalid configuration.

Default semantic-validation failure policy without `#[ValidationFailed]`:

- `/api/*` routes return the canonical `422` envelope (`error.code =
  validation_failed`, `error.details` with normalized field errors).
- Other JSON requests return a structured JSON failure response.
- Browser and Inertia requests redirect back to the `Referer` (or `/`), receive
  an error notification, validation errors, and no persisted old input.

The former `/auth/check-email` endpoint has been removed. Registration does not expose email availability.

See [the DTO migration template](development/request-validation.md) for required,
optional, enum, array and partial PATCH conventions and documented exceptions.

Validation failures are expected client input: they are never logged, and
request bodies, mapped DTO values, passwords, and tokens never reach logs or
error reports.

## Pagination

Paginated endpoints accept:

- `page`: 1-based page number.
- `per_page`: page size, at most 100.
- `search`: supported where the underlying query supports it.

Paginated responses use:

```json
{
  "data": [],
  "meta": {
    "total": 0,
    "current_page": 1,
    "per_page": 20,
    "last_page": 1,
    "from": 0,
    "to": 0
  },
  "links": {
    "first": "...",
    "prev": null,
    "next": null,
    "last": "..."
  }
}
```

`GET /api/v1/admin/users` is paginated. It returns page 1 with 20 users by
default and accepts at most 100 users through `per_page`. Existing clients
that expected every user in one response must follow `links.next` until it is
`null`.

It accepts `search` for case-insensitive substring matching on email or display
name. Search characters `%`, `_`, and `\` are literal, not wildcard operators.
The `status` filter accepts `active` or `banned`. Pagination links preserve accepted filters and use
their normalized page values. The endpoint always orders results by email
ascending and then UUID ascending using the PostgreSQL database collation;
this can differ from the previous PHP bytewise email ordering. `sort` and
`direction` do not change this fixed order.

## Token Examples

Create a user REST API token:

```bash
curl -X POST http://localhost:8080/api/v1/user/api-tokens \
  -H "Authorization: Bearer $PACKIO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"CI automation","scopes":["read","write"]}'
```

Regenerate a user REST API token:

```bash
curl -X PUT http://localhost:8080/api/v1/user/api-tokens/$TOKEN_ID/regenerate \
  -H "Authorization: Bearer $PACKIO_API_TOKEN"
```

Create a Composer registry token for an organization:

```bash
curl -X POST http://localhost:8080/api/v1/organizations/acme/registry-tokens \
  -H "Authorization: Bearer $PACKIO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Composer automation"}'
```

## Hardening

- API token create/regenerate and registry-token create/regenerate endpoints are rate limited with the `api_token_create` policy.
- Successful API write requests on organization-scoped routes (`#[ApiOrganizationContext]`) and `#[ApiAudited]` routes (admin, user API-token writes and organization creation) are recorded in the audit log with route, method, status, path, and API token id context.
- API POST/PUT/PATCH/DELETE routes are CSRF-exempt only through the explicit `#[ApiAuthenticated]` route metadata, which combines the `api` authentication profile with the exemption. They are stateless token-authenticated routes and do not accept a browser session as a credential; the `/api/v1` path prefix alone is never an exemption.
- Inbound provider webhook routes remain outside `/api/v1` and are not moved into the REST API namespace.
- CORS is globally piped before routing and enabled by default for configured origins only. Browser-based external API clients must use an origin listed in `CORS_ALLOWED_ORIGINS`; API preflight requests should include `Authorization`, `X-API-TOKEN`, `Content-Type`, and `Accept` as needed. `X-CSRF-Token` is intentionally absent from the default CORS policy because it is a same-origin web-session header, not an API transport header.

## Deployment

- `/api/doc.json` and `/api/v1/doc.json` are generated by the application once per worker; `public/openapi.json` is the committed artifact checked by `composer openapi-check`. It is not shipped in the runtime image.
- `/api/doc` is handled by the standard Mezzio handler path and serves Swagger UI.
- After config changes, run `composer clear-config-cache` or restart the dev server if it keeps stale routes/config.
- In local development, `composer serve` exposes Swagger UI at `http://localhost:8080/api/doc`.

## Compatibility Policy

- Additive changes are allowed in `/api/v1`.
- Breaking contract changes require a new version prefix such as `/api/v2`.
- Repman-compatible behavior is preserved where it maps cleanly: `X-API-TOKEN` is supported, and organization/package/token automation exists under Packio-native versioned paths.
