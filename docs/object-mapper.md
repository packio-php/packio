# Object mapper

Packio uses `sirix/object-mapper` 0.10 for explicit, trusted object-to-object
DTO projections. It is not a serializer, an input mapper, a policy engine, or
a substitute for application services that require repositories, secrets,
actor context, or current time.

Each conventional mapping belongs to its owning module's
`config/object-mapper.config.php`. Common owns the shared mapper wiring and
value-transformer registry.

Mappings use exact runtime source matching by default. Approved Cycle entity
projections may opt in per pair to `source_match: cycle_proxy`. This accepts
only the configured entity or its direct Cycle `EntityProxyInterface` child;
ordinary subclasses, indirect proxies, and provider-backed definitions remain
exact-only. The setting does not preload relations or change responsibility for
lazy-loading and N+1 behaviour.

## Mapping configuration

Register an exact source-to-target pair under `object_mapper.mappings`. Public
source properties must either be mapped or listed in `ignored_source`.

```php
Source::class . '->' . SourceDto::class => [
    'source' => Source::class,
    'target' => SourceDto::class,
    'rules' => [
        'id' => [
            'method' => 'getIdentifier',
            'transformer' => UuidInterfaceToStringTransformer::class,
        ],
        'token' => [
            'property' => 'token',
            'nested' => TokenDto::class,
        ],
        'items' => [
            'property' => 'items',
            'collection' => [
                'source' => Item::class,
                'target' => ItemDto::class,
            ],
        ],
    ],
    'ignored_source' => ['internalValue'],
],

// Only for an approved direct Cycle entity -> DTO pair.
Entity::class . '->' . EntityDto::class => [
    'source' => Entity::class,
    'target' => EntityDto::class,
    'source_match' => 'cycle_proxy',
    'rules' => [],
],
```

Each rule has exactly one selector: `property`, `getter`, or `method`. It has
either no terminal operation (direct mapping) or exactly one of:

| Operation | Purpose |
| --- | --- |
| `transformer` | Uses an explicitly registered, type-compatible transformer class. |
| `nested` | Maps one object through an exact registered source/target pair. |
| `collection` | Maps `array` or `?array` values through explicit source and target element classes. |
| `constant` | Assigns one trusted literal scalar or `null`, without reading a source member. |

`transformer` cannot be combined with structural operations. `nested` only
accepts an exact pair; `collection` only supports homogeneous runtime object
elements, `array`/`?array` source and target types, preserves input order, and
returns a list. Iterables, keyed output, PHPDoc element inference, and implicit
casts are unsupported. Invalid grammar, missing pairs, incompatible types, and
direct or indirect nested cycles fail mapper warmup before traffic.

`constant` is deliberately closed: it accepts only `null`, `bool`, `int`, a
finite `float`, or `string`, and it cannot be combined with a selector,
`transformer`, `nested`, or `collection`. Its literal is emitted into generated
cache code, so it is never appropriate for a token, PII, ciphertext, request
data, or policy-derived value. Packio currently registers no production
constant. Provider-backed custom mappings are deliberately unused and remain
exact-only.

Common registers five deterministic transformers: empty string to null, UUID
to string, Chronos to `DATE_ATOM`, nullable Chronos to legacy empty string, and
nullable Chronos to nullable atom string. Transformers never log mapped values.

The Organization module registers one exception: `InvitationTokenTransformer`
decrypts the stored invitation token during the
`OrganizationInvitation -> OrganizationInvitationDto` mapping. It is the only
transformer that handles a secret.

## Factory regression coverage

`ObjectMapperFactoryTest` verifies direct, transformer, nested, and collection
mapping generation with the shared registries. It also verifies every grammar
rejection (missing or multiple selectors, multiple terminal operations, extra
keys, malformed collection maps, invalid structural class names, and wrong
transformer classes), plus full rule-path diagnostics. Warmup coverage asserts
missing nested pairs and deterministic nested-cycle diagnostics; a mapped
collection with a wrong element asserts the package's safe parameter/key/type
runtime diagnostic. The tests deliberately do not inspect generated PHP or
simulate Cycle proxy input; that is covered by direct entity and
PostgreSQL/Cycle-proxy integration tests.

## Production warmup

Object mapper cache format is `8` in 0.10. Cache files generated by earlier
formats, including `7`, are intentionally not reusable. The application
isolates format-8 files in the `v8` subdirectory of `OBJECT_MAPPER_CACHE_DIR`,
so an old running release retains its mapper cache while the published release
is warmed. The content-addressed format-8 files may coexist across releases; do
not delete them before the process restart. After publish, rotate to a fresh
`0700` directory owned by the runtime user, clear the config cache when it is
enabled, and warm the mapper before restarting HTTP or worker processes.
Generated files must remain `0600`:

```bash
composer clear-config-cache
APP_PRODUCTION=true OBJECT_MAPPER_GENERATE_ON_DEMAND=0 php vendor/bin/laminas object-mapper:warmup
```

Production must keep `OBJECT_MAPPER_GENERATE_ON_DEMAND=0`. The warmup output
identifies mapping pairs and compilation diagnostics, not mapped payloads.
In production, long-running HTTP workers also warm their process-local prepared
mapper entries during bootstrap, before accepting traffic. This enables 0.10's
prepared-mapping reuse; service restart after every mapper-related deployment
remains mandatory.

## Projection inventory

The following safe projections are conventional mappings: provider resources,
source OAuth account, `SourceProviderInstanceDependencies`,
`WebhookRegistrationResult`, worker job log, trusted Identity results
(`IdentityUserResult -> UserDto`, `ApiAccessToken -> ApiAccessTokenResult`,
`ApiAccessTokenResult`, `IssuedRegistryAccessToken`,
`RegistryAccessTokenResult`, `PasswordResetResult`), issued API access tokens
(the one nested rollout), and the approved User, Package, Audit, Webhook,
Organization, OrganizationMember, and OrganizationInvitation Cycle entity
projections.

Manual mappings remain intentional when they carry a boundary policy:

| Site | Status | Reason |
| --- | --- | --- |
| `Release -> ReleaseDto` | Requires business logic/security | Removes internal storage data. |
| `Source -> SourceDto` | Requires external context | Performs provider authorization lookup and derives authorization fields. |
| `ProviderAuthorization -> ProviderAuthorizationDto` | Requires business logic/security | Decrypts and masks a token. |
| `SourceProviderInstance -> SourceProviderInstanceDto` | Requires business logic/security | Derives client-secret state. |
| `ProviderDescriptor -> SourceProviderDto` | Requires external context | Computes capabilities and OAuth availability through a resolver. |
| `RegistryAccessToken` entity | Requires business logic/security | Enforces the plaintext-token boundary. |
| `Job -> JobDto` | Requires external context | Receives `warningCount` separately from the entity. |
| `PublicationSyncResult -> PublicationSyncResultDto` | Requires unsupported untyped input | Translates heterogeneous `mixed` arrays, defaults, casts, and legacy aliases. |
| Generic `PaginatedResultDto` assembly | Requires external context | Wraps query metadata rather than projecting a stable domain object. |
